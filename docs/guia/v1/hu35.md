# HU-35 · Respaldo y restauración

Ficha con la narrativa, los mockups y los criterios: `fichas/sprint5/hu35.pdf`.

## De dónde parte

Última historia del proyecto, y la única del módulo de administración y seguridad que
quedaba pendiente.

## Decisiones

- **El respaldo se genera en PHP, no con `pg_dump`.** El alojamiento de destino no tiene
  consola remota (ver `docs/despliegue.md`): el sistema tiene que poder respaldarse solo,
  y el archivo resultante tiene que servir para importarlo desde el panel del proveedor.
- **Es un respaldo de datos, no de esquema.** El esquema lo crean las migraciones. El
  guion vacía las tablas, repone las filas y ajusta las secuencias, todo dentro de una
  transacción: o entra completo o no entra nada.
- **Las filas se reponen en orden de dependencias.** El orden alfabético no sirve
  ---`permission_role` iría antes que `roles`--- y las claves foráneas de Laravel no son
  diferibles, así que las tablas se ordenan topológicamente con `Schema::getForeignKeys`.
- **Sin las secuencias, el sistema queda roto.** Tras restaurar, el primer registro nuevo
  chocaría con un identificador ya usado: por eso cada tabla con `id` lleva su `setval`.
  Hay una prueba que lo verifica registrando algo nuevo después de restaurar.
- **El asiento de la restauración se escribe después, no antes.** La propia restauración
  vacía la bitácora y se llevaría por delante el asiento de lo que se está haciendo. La
  bitácora queda como estaba en el respaldo, más la constancia de esta operación.
- **Quien restaura puede no existir en el respaldo.** Si su cuenta se creó después, el
  asiento queda sin autor y lo dice, antes que fallar por una clave foránea.
- **El nombre del archivo se valida contra un patrón.** Llega por la dirección: nada que
  no sea un respaldo de este sistema puede convertirse en una ruta de disco.
- **Las tablas de trabajo de Laravel quedan fuera** (`sessions`, `cache`, `jobs`…):
  restaurarlas solo serviría para revivir sesiones viejas.

## Backend

| Capa | Archivos |
|---|---|
| Domain | `Exceptions/RespaldoNoEncontradoException` |
| Application · Actions | `GenerarRespaldo`, `RestaurarRespaldo` |
| Application · Contracts | `RespaldoGateway` |
| Application · DTOs | `RespaldoData` |
| Http · Controllers | `RespaldoController` |
| Infrastructure · Files | `RespaldoSqlEnDisco` |
| Consola | `respaldo:generar` y su tarea programada, en `routes/console.php` |

### API

Exigen sesión y el permiso `respaldo_restauracion`.

| Método | Ruta | Respuestas |
|---|---|---|
| GET | `/api/respaldos` | 200 con los respaldos, del más nuevo al más viejo |
| POST | `/api/respaldos` | 201 con el archivo, las tablas y las filas |
| GET | `/api/respaldos/{archivo}` | 200 con el guion SQL adjunto; 404 si no existe |
| POST | `/api/respaldos/{archivo}/restaurar` | 200; 404 si el respaldo no existe |

### Operaciones que deja en la bitácora

`respaldo.generar`, `respaldo.restaurar`.

## Programación

```
Schedule::command('respaldo:generar')->dailyAt('02:00')->withoutOverlapping();
```

En el servidor se da de alta una sola tarea `cron` que llama a `schedule:run` cada
minuto; el procedimiento está en `docs/despliegue.md`, sección 5.

## Frontend

`paginas/admin/Respaldos.jsx`: el botón de generar, la lista con tamaño y fecha, la
descarga y la restauración, que exige confirmar en un aviso rojo antes de reemplazar
todos los datos.
