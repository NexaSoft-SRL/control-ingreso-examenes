# HU-17 · Generación de códigos QR

Ficha con la narrativa, los mockups y los criterios: `fichas/sprint3/hu17.pdf`.

## De dónde parte

Historia nueva y la primera que suma una dependencia externa al proyecto:
`endroid/qr-code` para dibujar el código.

## Decisiones

- **El código es un token opaco de 48 caracteres al azar**, no un identificador
  codificado. Si el QR llevara el código universitario o el identificador del estudiante,
  fotografiar la tarjeta de otro bastaría para conocer sus datos o fabricar un código
  ajeno.
- **Un token por estudiante y examen**, con índice único. El mismo estudiante en dos
  exámenes lleva dos tarjetas distintas, y por eso HU-18 puede rechazar el código de otro
  examen.
- **Solo se emiten códigos para los habilitados.** Quien no rinde no necesita tarjeta, y
  emitirla daría la impresión de que puede entrar.
- **La reemisión es incremental.** Volver a emitir alcanza solo a quienes no tienen
  código: así se puede emitir el lote, habilitar a alguien más y volver a emitir sin
  invalidar las tarjetas ya repartidas.
- **La exportación es una hoja HTML que el navegador imprime.** Generar un PDF sumaría
  otra dependencia para resolver algo que el navegador ya hace, y la hoja se puede enviar
  por correo tal cual.
- **El dibujo del código vive en `Infrastructure/QR`.** La capa de aplicación conoce el
  token; la librería solo aparece en la infraestructura, cubierta por su propia regla en
  Deptrac.

### API

Todas exigen sesión y el permiso `codigos_qr`.

| Método | Ruta | Respuestas |
|---|---|---|
| GET | `/api/examenes/{examen}/codigos-qr` | 200 con los códigos emitidos |
| POST | `/api/examenes/{examen}/codigos-qr` | 200 con cuántos se emitieron |
| GET | `/api/examenes/{examen}/codigos-qr/hoja` | 200 con la hoja para imprimir |

### Operaciones que deja en la bitácora

`qr.emitir`.

## Frontend

`paginas/ingreso/CodigosQr.jsx`, en `/admin/codigos-qr`: elegir el examen, emitir los
pendientes, ver el listado y abrir la hoja. El token no se muestra nunca en la interfaz.
